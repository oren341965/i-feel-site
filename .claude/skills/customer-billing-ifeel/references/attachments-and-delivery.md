# Billing files and verified mail delivery

## Resolve and download

Build a private manifest for this customer: source file ID/path/revision, purpose, filename, local location, size, and the matched customer/project or quotation number. Include the current payment summary and only the relevant quotations/requested supporting documents. Inspect contents; generic filenames such as `HashDoc_*.pdf` are not a customer identity.

Download actual files when the user asks for attachments. A Dropbox link or the sentence “מצורפים קבצים” is not a file attachment. Use a link instead only if that delivery form was requested. Verify downloads are nonempty, open correctly and contain the current values. If a PDF summary is requested, render from the verified final workbook and check Hebrew, dates, page boundaries and totals.

In a remote-desktop workflow the local and remote Downloads folders belong to different computers. Files must exist on the computer where the mail compose window uploads them. Never assume a local tool download appeared on the remote machine. The Dropbox web account may expose files absent from selective desktop sync.

## Prepare the exact message

- Confirm From mailbox, To, CC and thread from the user's instruction and authoritative correspondence. Do not reuse recipients/CC from another customer or infer an email address from a name.
- Inspect the current thread and Sent items for the same request before creating or sending. A stale draft may have been superseded by a reply, payment or another operator's send.
- Compose a short Hebrew message matching the verified amount and current due stage. Do not invent bank instructions, due dates or discounts. Refer only to documents that will actually be attached.
- Attach each manifest file, wait for upload completion, and inspect the compose window's attachment list/count/names. Reopen or inspect attachments when generic names, same-name versions or content ambiguity remain. Verify recipients and message after attachment operations.

## Send authority and result

If Oren explicitly requested sending this customer billing package to an identified recipient, proceed within that scope; do not re-request already supplied authorization. Otherwise keep the fully prepared draft and request only the missing send decision. Creating this skill is not standing permission to send all future bills. Maya's routine customer-mail authority does not automatically cover financial demands.

After sending, inspect Sent items/provider result for the matching recipient, subject/thread, send time and attachment list. “Send clicked”, a vanished compose window or an Outbox item is not proof of delivery to Sent. Report provider acceptance/Sent confirmation, not recipient reading or bank payment.

If the send outcome is ambiguous, inspect Sent/Outbox/thread before retrying. Do not send a second copy to obtain clearer evidence. Record the message/draft ID or visible sent reference privately for safe resumption. Report a bounce or failed send accurately; do not silently switch recipients.
