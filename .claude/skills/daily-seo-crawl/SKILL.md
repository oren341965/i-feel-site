# Daily SEO/AEO/GEO Crawl 3.1 — i-feel.co.il

## 🎯 North Star — מטרת העל

**i-feel.co.il במקום #1 בחיפוש אורגני בגוגל ישראל עבור:**
1. **`בית חכם`** — שולט על מסלול הלקוחות הפרטיים
2. **`בקרת מבנה`** — שולט על מסלול ה-BMS ומבני ציבור

כל ריצה של הסקיל הזה צריכה לקדם אותנו לעבר היעד הזה. הסקיל לא *מנטר* SEO — הוא *מקדם* את i-feel למעלה ב-SERP וגם משפר AEO/GEO כך שמנועי AI יוכלו לזהות את I FEEL כישות מקצועית, לאחזר תשובות מדויקות מהאתר ולצטט אותו כאשר קיימת התאמה לשאלה. אם הדוח לא מקרב אותנו למהלך ההתקפי הבא — חזור על התהליך.

מילת מפתח משנית (tier-2), למעקב בהמשך: `דירה חכמה` (מסלול היזמים — "razor" בעסקי הבית החכם).

## איך הדוח עוזר להגיע ל-#1

אורן קורא את הדוח 30-60 שניות בבוקר. צריך לצאת ממנו:
1. **היכן אנחנו היום** על שתי מילות העל (מיקום ומי מחזיק את #1-#3)
2. **מה הפער** — מה יש לאלה שמעלינו, שאין לנו
3. **המהלך ההתקפי הבא** — פעולה אחת שמקדמת אותנו (פוסט חדש, שיפור תוכן קיים, backlink, תיקון טכני שחוסם אותנו)

גרסאות 1.0 ו-2.0 הפיקו דוח ארוך ומגנתי (ציון, טבלאות, PSI). 3.0 מבוסס על:
- **Delta over state** — מה השתנה, לא מה קיים
- **Offensive over defensive** — מהלכים לקידום, לא רק תחזוקה
- **North Star focus** — 2 מילות על נמדדות עם קונטקסט תחרותי מלא; שאר המילים — רק שורה אחת

## מבנה הריצה

| מצב | מתי | כמה זמן | מה נסרק |
|-----|-----|---------|----------|
| `daily` (ברירת מחדל) | ימי חול, 07:00 | ~90 שניות | דף הבית + הפוסט האחרון |
| `deep` | יום ראשון, 07:00 | ~5 דקות | + 5 דפים קריטיים + מתחרים |
| `verify` | לפי בקשה | ~30 שניות | URL ספציפי לבדיקה של תיקון |

בברירת מחדל — תמיד `daily`. `deep` רק אם היום ראשון או אם אורן ביקש "סריקה מלאה"/"deep scan". `verify` כשאורן כותב "תבדוק שהתיקון עבד ב-{url}".

## סדר הפעולות

### 1. שליפת בייסליין מאתמול (15 שניות)
`conversation_search` עם query "דוח SEO יומי i-feel" — שלוף את הדוח של אתמול. זה מה שמאפשר דלתא. אם לא נמצא דוח קודם → זו ריצת bootstrap, ציין זאת בתחתית הדוח ורשום ערכים נוכחיים כבסיס.

### 2. סריקה ממוקדת (30-60 שניות)

> **קנוני = ללא `www`.** כל הכתובות בסקיל הזה הן `https://i-feel.co.il/...`. ה-`www` מפנה 301 ל-non-www (הגירה הושלמה 21/07/2026) — אל תשתמש בו ואל תדווח עליו כחסם. ראה "מלכודות ידועות".

**תמיד — דף הבית**:
`web_fetch https://i-feel.co.il/`

**תמיד — המאמר האחרון**:
`web_fetch https://i-feel.co.il/sitemap.xml` → מצא את ה-`<url>` תחת `/articles/` עם ה-`<lastmod>` הכי חדש → `web_fetch` למאמר עצמו.
(אין `post-sitemap.xml` — האתר סטטי (Astro), sitemap יחיד ידני.)

**במצב `deep` בלבד — 4 דפים קריטיים**:
```
/smart-home/                  (לקוחות פרטיים)
/structure-control/           (BMS — עמוד העוגן ל"בקרת מבנה")
/contractor-customer-care/    (יזמים/קבלנים)
/contactus/                   (המרה)
```
> עודכן 21/07/2026: `/construction-developers-2/` ו-`/quote-2/` הוחלפו — שניהם מתו בהגירה (410).
> לפני שמוסיפים דף לרשימה — לוודא שהוא מחזיר 200 בפועל.

לכל דף — בדוק:
- HTTP status (צריך 200)
- `<h1>` count (בדיוק 1)
- `<title>` length (50-60 תווים)
- `<meta name="description">` (120-160 תווים)
- `<link rel="canonical">` נכון
- JSON-LD schema קיים
- og:title ו-og:image
- alt coverage (תן הערכה גסה — לא חייב מדויק)

**חשוב**: רק ממצאים שמסווגים 🔴 או 🟡 נכנסים לדוח. בדיקה שעברה בהצלחה לא מוזכרת.

### 3. Core Web Vitals (10 שניות)
קריאה אחת ל-PSI API לדף הבית, mobile בלבד (במצב `deep` גם desktop):

```
https://www.googleapis.com/pagespeedonline/v5/runPagespeed?url=https://i-feel.co.il/&strategy=mobile
```

שלוף רק 4 ערכים: Performance score, LCP, CLS, TBT. **ציין בדוח רק** אם:
- ירידה של ≥5 נקודות בציון Performance
- מעבר סף (למשל LCP מתחת 2.5 → מעל 2.5)
- CLS עבר 0.5 במובייל

אחרת — אל תזכיר. יציב = לא מדווחים.

### 4. אימות הפוסט היומי (20 שניות)
הפוסט נוצר ע"י סקיל נפרד (`daily-article-publisher`). כאן רק מאמתים שעלה תקין:

- ✅ Featured image מוצג (`<meta property="og:image">` — ולוודא שהיא **ייעודית**, לא `og-cover.jpg` הגנרי)
- ✅ Word count ≥ 1,500
- ✅ Article או BlogPosting schema ב-JSON-LD
- ✅ Meta description קיים
- ✅ אינדוקס: `web_search: site:i-feel.co.il {כותרת}` — אם מופיע → ✅. אם עברו פחות מ-48 שעות מהפרסום → ⏳ (תקין). מעל 48 שעות ולא מאונדקס → 🔴.

### 5. מעקב North Star + מילות מפתח (30 שניות)

זה הסעיף הכי חשוב של הסקיל. הוא נותן את הקונטקסט להחלטות האסטרטגיות.

**לכל אחת משתי מילות העל** (`בית חכם`, `בקרת מבנה`):

א. `web_search: {keyword}` — שלוף את top 5 התוצאות.
ב. זהה את המיקום של `i-feel.co.il`. אם לא בתוצאות — סמן "מחוץ ל-top 5".
ג. תיעד מי מחזיק את #1, #2, #3.
ד. השווה ל-`conversation_search` של אתמול:
   - האם המיקום שלנו השתנה?
   - האם מתחרה חדש נכנס ל-top 3?
   - האם מישהו שהיה מעלינו נפל?

ה. **ניתוח פער** — לדף המחזיק ב-#1: `web_fetch` ונתח:
   - מה הכותרת (<title>)
   - מה ה-H1
   - אורך התוכן (גס)
   - האם יש schema עשיר (FAQ, HowTo, Article)
   - האם יש תמונות/וידאו
   - כמה H2 (מעמיקות התוכן)

ו. השווה לדף שלנו שמדורג על המילה הזו (אם יש — `web_search: site:i-feel.co.il {keyword}` → הדף הראשון).

ז. גבש **מהלך התקפי אחד** — המשימה השבועית שהכי תקרב אותנו ל-#1. דוגמאות:
   - "הפוסט של Vitrea 2,400 מילים, שלנו 800 → להרחיב פוסט קיים ל-2,500+"
   - "#1 יש FAQ schema, לנו אין → להוסיף 8 שאלות"
   - "#1 יש 3 סרטונים, לנו אין → להוסיף סרטון מה-YouTube שלנו"
   - "Higoal קפץ מ-#8 ל-#4 על 'בקרת מבנה' → לבדוק מה הם עשו"

**למילה ה-tier-2** (`דירה חכמה`) — רק שורה אחת: מיקום נוכחי + שינוי מאתמול.

**הערה טכנית**: בהיעדר Google Search Console API מוסמך, המיקומים הם *משוערים* מתוך `web_search`. ציין זאת בדוח. אם GSC MCP זמין — עדיף להשתמש בו לקבלת מיקום מדויק.

**בדיקת מוכנות עמוד לציטוט AI — עמוד אחד בכל יום:**
בחר את העמוד הקריטי ביותר לפי שאילתות היום ובדוק:
- תשובה ישירה של 2-4 משפטים בתחילת הסעיף המרכזי.
- FAQ טבעי שעונה על שאלות משתמשים אמיתיות.
- עובדות, מספרים, שמות טכנולוגיות ונתונים הניתנים לאימות.
- שם הישות I FEEL / i-feel / איי פיל באופן עקבי ובהקשר ברור.
- קישור ברור בין I FEEL לבין KNX / BMS / Siemens Desigo / Smart Home לפי נושא העמוד.
- קישורים פנימיים לעמודי עוגן רלוונטיים.
- Schema מתאים וקיים; אין להוסיף schema שאינו משקף תוכן נראה.
- רעננות/תאריך עדכון כאשר הנושא משתנה עם הזמן.
- עברית ואנגלית כאשר קיימת הצדקה אמיתית לחיפוש בינלאומי.

**Entity consistency — בדיקה יומית קצרה:**
- הניסוח המועדף: `I FEEL היא Siemens Solution Partner בתחום Building Automation`.
- אם נמצא ניסוח `נציגת Siemens בישראל` או ניסוח שמשמעותו בלעדיות/נציגות רשמית, סמן לבדיקה אלא אם קיימת אסמכתא רשמית עדכנית.
- בדוק עקביות בשם החברה, תחומי הפעילות, טלפון, כתובת ופרטי קשר בין האתר למקורות חיצוניים רלוונטיים.

**Off-site GEO / Authority — הזדמנות אחת בכל deep:**
חפש הזדמנות איכותית אחת לפחות לאזכור או backlink ממקור מקצועי רלוונטי: KNX Association, Siemens, ספק/יצרן, יועץ חשמל, מהנדס, אתר פרויקט, פורטל מקצועי או פרופיל עסקי סמכותי. אין ליצור ספאם, אינדקסים חלשים או קישורים מלאכותיים.

**Case study / answer opportunity:**
אם שאילתת יעד אינה מכוסה היטב, העדף שיפור עמוד קיים או Case Study במבנה:
בעיה → סוג המבנה → הפתרון → הטכנולוגיה → מה הותקן → היקף/מספרים → תוצאה.
עובדות ניתנות לאימות עדיפות על ניסוח שיווקי כללי.

**פעולת GEO יומית:**
הצע פעולה אחת בלבד, בעלת ההשפעה הגבוהה ביותר, מתוך:
- הוספת/שיפור תשובה ישירה.

### כללי הצגה

## הכנת Draft PR בסוף ריצה — ללא merge אוטומטי

אם הוחל שינוי בקוד או בתוכן במהלך ריצה שאורן ביקש, סוגרים אוטומטית רק את החלק המקומי וההפיך: ענף עבודה, בדיקות, commit, העלאת הענף ו־Draft PR. merge ל־`main`, אישור production ופריסה נשארים שער אישור מפורש ונפרד.

1. צור ענף ייחודי באמצעות `scripts/workstations/new-work.ps1 -Slug <short-seo-slug>` לפני העריכה. אין לשנות שם של ענף קיים ממחשב אחר.
2. בצע את התיקון המצומצם והריץ את בדיקות האתר.
3. פרסם דרך המסלול הבטוח:
   ```powershell
   .\scripts\workstations\publish-work.ps1 `
     -CommitMessage "SEO: <תיאור קצר>" `
     -PrTitle "SEO: <תיאור קצר>"
   ```
4. עצור ב־Draft PR ודווח את הקישור, הראיות והבדיקות. אל תפעיל auto-merge ואל תטפל ב־GitHub Token ידני.
5. רק לאחר אישור merge מפורש, מסלול `deploy-ifeel` רשאי להמשיך דרך GitHub Actions וה־runner המשרדי. אחרי פריסה מאושרת הרץ `verify-live`.

`scripts/deploy/seo-autopublish.mjs` נשמר כשם תאימות ישן, אך התנהגותו מוגבלת מעתה להאצלת העבודה ל־`publish-work.ps1` ולפתיחת Draft PR בלבד.

**נפילה בטוחה**: אם build, rebase, push או יצירת Draft PR נכשלים, אין לבצע force push, merge ידני, FTP או עקיפת runner. השאר את העבודה בענף ודווח את הסיבה.

## מלכודות ידועות — לקרוא לפני שמכריזים על "חסם טכני"

**כלל הזהב: אל תכריז על חסם טכני בלי לבדוק קוד סטטוס HTTP בפועל.**
מה שגוגל מציג ב-SERP הוא *תמונת עבר*, לא מצב השרת. דוח שמסיק "יש בעיית 301" מתוך תוצאות חיפוש — טועה.
לפני כל טענה על הפניות/סטטוס, לבצע בקשה אמיתית ולקרוא את הקוד. אם אין כלי HTTP זמין — לכתוב בדוח "לא אומת", לא להכריז.

**1. הגירת www הושלמה (21/07/2026) — לא לדווח עליה יותר.**
`www.i-feel.co.il/*` מחזיר 301 ל-`i-feel.co.il/*` (LiteSpeed, לא Netlify). אומת על כל הדפים.
העובדה שגוגל עדיין מציג כתובות `www` בתוצאות היא **פיגור עיבוד רגיל** שמתנקז מעצמו תוך שבועות — **זה לא חסם ולא דורש פעולה.**
דוח של 20/07 הכריז על זה כחסם ראשי במשך 6 ימים והפנה את כל המהלך ההתקפי לכיוון שגוי. לא לחזור על זה.

**2. עברית ב-`Location` — מקור לתוצאות 404 מזויפות.**
השרת מחזיר כותרת `Location` עם עברית ב-UTF-8 גולמי. כלים רבים (.NET/PowerShell) מפענחים כותרות כ-Latin-1 → הכתובת נהרסת → מעקב אחריה מחזיר 404 שגוי.
באודיט של 21/07 זה ייצר **54 ממצאי 404 מזויפים**. הפתרון: להמיר את המחרוזת בחזרה לבייטים ולפענח כ-UTF-8 לפני שעוקבים.
קידוד אחוזים (`%d7` מול `%D7`) **אינו** רגיש לאותיות — זו לא הבעיה.

**3. תקלות הגירה פתוחות** — הרשימה המלאה עם מיפוי 301 מוכן:
`ifeel-BMS projects/migration-audit-301-fixes-2026-07-21.md` (22 הפניות לתיקון; מתוכן 🔴 `/בית-חכם/` מחזיר 404 והוא מאונדקס בגוגל).
לפני שמדווחים על דף שבור — לבדוק אם הוא כבר ברשימה שם.

## Mandatory sitemap and 4xx gate

Before every production publish or SEO-driven page change, run a full live sitemap integrity check. Every URL listed in `public/sitemap.xml` must resolve on production to HTTP 200 after deploy. Any 4xx or 5xx response is a release-blocking SEO defect until investigated and corrected.

Rules:
- Never publish a new sitemap URL without verifying the exact live URL returns 200.
- Treat Unicode/Hebrew slugs as high-risk: verify UTF-8 encoding, canonical URL, internal links, generated route, and live server response. Prefer stable ASCII slugs when a Unicode slug causes encoding ambiguity or server inconsistency.
- Detect duplicate sitemap URLs and remove duplicates before release.
- If Google Search Console reports `Blocked due to other 4xx`, immediately identify the exact affected URLs, reproduce the live HTTP status, fix the route/link/sitemap source, redeploy, and re-check.
- After deployment, re-fetch the live sitemap and test every listed URL. Do not report the issue as fixed until the production crawl has zero unexpected 4xx/5xx results.
- Add this check to the daily SEO health review and to every `verify-live`/deployment verification flow.
- Record the root cause and prevention rule when a new class of indexing error is discovered, so the same failure is not repeated.
