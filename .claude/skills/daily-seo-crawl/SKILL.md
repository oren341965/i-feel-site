# Daily SEO Crawl 3.4 — i-feel.co.il

## 🎯 North Star — מטרת העל

**i-feel.co.il במקום #1 בחיפוש אורגני בגוגל ישראל עבור:**
1. **`בית חכם`** — שולט על מסלול הלקוחות הפרטיים
2. **`בקרת מבנה`** — שולט על מסלול ה-BMS ומבני ציבור

כל ריצה של הסקיל הזה צריכה לקדם אותנו לעבר היעד הזה. הסקיל לא *מנטר* SEO — הוא *מקדם* את i-feel למעלה ב-SERP. אם דוח שלך לא מקרב אותנו למהלך ההתקפי הבא — חזור על התהליך.

מילת מפתח משנית (tier-2), למעקב בהמשך: `דירה חכמה` (מסלול היזמים — "razor" בעסקי הבית החכם).

## איך הדוח עוזר להגיע ל-#1

אורן קורא את הדוח 30-60 שניות בבוקר. צריך לצאת ממנו:
1. **היכן אנחנו היום** על שתי מילות העל (מיקום ומי מחזיק את #1-#3)
2. **מה הפער** — מה יש לאלה שמעלינו, שאין לנו
3. **המהלך ההתקפי הבא** — פעולה אחת שמקדמת אותנו (פוסט חדש, שיפור תוכן קיים, backlink, תיקון טכני שחוסם אותנו)

גרסאות 1.0 ו-2.0 הפיקו דוח ארוך ומגנתי (ציון, טבלאות, PSI). 3.0 מבוסס על:
- **Delta over state** — מה השתנה, לא מה קיים
- **Offensive over defensive** — מהלכים לקידום, לא רק תחזוקה
- **North Star focus** — 2 מילות על נמדדות עם קונטקסט תחרותי מלא; שאר המילים — רק שורה אחת

## מבנה הריצה

| מצב | מתי | כמה זמן | מה נסרק |
|-----|-----|---------|----------|
| `daily` (ברירת מחדל) | ימי חול, 07:00 | ~90 שניות | דף הבית + הפוסט האחרון |
| `deep` | יום ראשון, 07:00 | ~5 דקות | + 5 דפים קריטיים + מתחרים |
| `verify` | לפי בקשה | ~30 שניות | URL ספציפי לבדיקה של תיקון |

בברירת מחדל — תמיד `daily`. `deep` רק אם היום ראשון או אם אורן ביקש "סריקה מלאה"/"deep scan". `verify` כשאורן כותב "תבדוק שהתיקון עבד ב-{url}".

## סדר הפעולות

### 1. שליפת בייסליין מאתמול (15 שניות)
`conversation_search` עם query "דוח SEO יומי i-feel" — שלוף את הדוח של אתמול. זה מה שמאפשר דלתא. אם לא נמצא דוח קודם → זו ריצת bootstrap, ציין זאת בתחתית הדוח ורשום ערכים נוכחיים כבסיס.

### 2. סריקה ממוקדת (30-60 שניות)

> **קנוני = ללא `www`.** כל הכתובות בסקיל הזה הן `https://i-feel.co.il/...`. ה-`www` מפנה 301 ל-non-www (הגירה הושלמה 21/07/2026) — אל תשתמש בו ואל תדווח עליו כחסם. ראה "מלכודות ידועות".

**תמיד — דף הבית**:
`web_fetch https://i-feel.co.il/`

**תמיד — המאמר האחרון**:
`web_fetch https://i-feel.co.il/sitemap.xml` → מצא את ה-`<url>` תחת `/articles/` עם ה-`<lastmod>` הכי חדש → `web_fetch` למאמר עצמו.
(אין `post-sitemap.xml` — האתר סטטי (Astro), sitemap יחיד ידני.)

**במצב `deep` בלבד — 4 דפים קריטיים**:
```
/smart-home/                  (לקוחות פרטיים)
/structure-control/           (BMS — עמוד העוגן ל"בקרת מבנה")
/contractor-customer-care/    (יזמים/קבלנים)
/contactus/                   (המרה)
```
> עודכן 21/07/2026: `/construction-developers-2/` ו-`/quote-2/` הוחלפו — שניהם מתו בהגירה (410).
> לפני שמוסיפים דף לרשימה — לוודא שהוא מחזיר 200 בפועל.

לכל דף — בדוק:
- HTTP status (צריך 200)
- `<h1>` count (בדיוק 1)
- `<title>` length (50-60 תווים)
- `<meta name="description">` (120-160 תווים)
- `<link rel="canonical">` נכון
- JSON-LD schema קיים
- og:title ו-og:image
- alt coverage (תן הערכה גסה — לא חייב מדויק)

**חשוב**: רק ממצאים שמסווגים 🔴 או 🟡 נכנסים לדוח. בדיקה שעברה בהצלחה לא מוזכרת.

### 3. Core Web Vitals (10 שניות)
קריאה אחת ל-PSI API לדף הבית, mobile בלבד (במצב `deep` גם desktop):

```
https://www.googleapis.com/pagespeedonline/v5/runPagespeed?url=https://i-feel.co.il/&strategy=mobile
```

שלוף רק 4 ערכים: Performance score, LCP, CLS, TBT. **ציין בדוח רק** אם:
- ירידה של ≥5 נקודות בציון Performance
- מעבר סף (למשל LCP מתחת 2.5 → מעל 2.5)
- CLS עבר 0.5 במובייל

אחרת — אל תזכיר. יציב = לא מדווחים.

### 4. אימות הפוסט היומי (20 שניות)
הפוסט נוצר ע"י סקיל נפרד (`daily-article-publisher`). כאן רק מאמתים שעלה תקין:

- ✅ Featured image מוצג (`<meta property="og:image">` — ולוודא שהיא **ייעודית**, לא `og-cover.jpg` הגנרי)
- ✅ Word count ≥ 1,500
- ✅ Article או BlogPosting schema ב-JSON-LD
- ✅ Meta description קיים
- ✅ אינדוקס: `web_search: site:i-feel.co.il {כותרת}` — אם מופיע → ✅. אם עברו פחות מ-48 שעות מהפרסום → ⏳ (תקין). מעל 48 שעות ולא מאונדקס → 🔴.

### 5. מעקב North Star + מילות מפתח (30 שניות)

זה הסעיף הכי חשוב של הסקיל. הוא נותן את הקונטקסט להחלטות האסטרטגיות.

**לכל אחת משתי מילות העל** (`בית חכם`, `בקרת מבנה`):

א. `web_search: {keyword}` — שלוף את top 5 התוצאות.
ב. זהה את המיקום של `i-feel.co.il`. אם לא בתוצאות — סמן "מחוץ ל-top 5".
ג. תיעד מי מחזיק את #1, #2, #3.
ד. השווה ל-`conversation_search` של אתמול:
   - האם המיקום שלנו השתנה?
   - האם מתחרה חדש נכנס ל-top 3?
   - האם מישהו שהיה מעלינו נפל?

ה. **ניתוח פער** — לדף המחזיק ב-#1: `web_fetch` ונתח:
   - מה הכותרת (<title>)
   - מה ה-H1
   - אורך התוכן (גס)
   - האם יש schema עשיר (FAQ, HowTo, Article)
   - האם יש תמונות/וידאו
   - כמה H2 (מעמיקות התוכן)

ו. השווה לדף שלנו שמדורג על המילה הזו (אם יש — `web_search: site:i-feel.co.il {keyword}` → הדף הראשון).

ז. גבש **מהלך התקפי אחד** — המשימה השבועית שהכי תקרב אותנו ל-#1. דוגמאות:
   - "הפוסט של Vitrea 2,400 מילים, שלנו 800 → להרחיב פוסט קיים ל-2,500+"
   - "#1 יש FAQ schema, לנו אין → להוסיף 8 שאלות"
   - "#1 יש 3 סרטונים, לנו אין → להוסיף סרטון מה-YouTube שלנו"
   - "Higoal קפץ מ-#8 ל-#4 על 'בקרת מבנה' → לבדוק מה הם עשו"

**למילה ה-tier-2** (`דירה חכמה`) — רק שורה אחת: מיקום נוכחי + שינוי מאתמול.

**הערה טכנית**: בהיעדר Google Search Console API מוסמך, המיקומים הם *משוערים* מתוך `web_search`. ציין זאת בדוח. אם GSC MCP זמין — עדיף להשתמש בו לקבלת מיקום מדויק.

## תיקונים אוטומטיים

> **האתר סטטי (Astro), לא WordPress.** אין WordPress MCP ואין Yoast. כל תיקון =
> ענף `work/seo-*` חדש מה-`origin/main` → build ובדיקות → Draft PR דרך המסלול הבטוח.
> merge ופריסה מתקיימים רק לאחר אישור מפורש, ואז `deploy.yml` ו־`verify-live` סוגרים את הלולאה.
> אין עריכה ישירה של `main` ואין העלאת FTP ידנית.

**רשאי לתקן ישירות** (ללא אישור נוסף, אחרי שהצעת ואורן אמר "תתקן"):
- הוספת/תיקון meta description בדף בודד
- הוספת alt לתמונה בודדת חסרה
- הוספת דף חסר ל-`public/sitemap.xml` (ה-sitemap ידני!)

**אסור לתקן ללא אישור מפורש**:
- שינוי `<title>` או `<h1>`
- שינוי canonical
- שינוי `robots.txt`
- מחיקת תוכן
- שינוי סוג schema

## הכנת Draft PR בסוף ריצה — ללא merge אוטומטי

אם הוחל שינוי בקוד או בתוכן במהלך ריצה שאורן ביקש, סוגרים אוטומטית רק את החלק המקומי וההפיך: ענף עבודה, בדיקות, commit, העלאת הענף ו־Draft PR. merge ל־`main`, אישור production ופריסה נשארים שער אישור מפורש ונפרד.

1. צור ענף ייחודי באמצעות `scripts/workstations/new-work.ps1 -Slug <short-seo-slug>` לפני העריכה. אין לשנות שם של ענף קיים ממחשב אחר.
2. בצע את התיקון המצומצם והריץ את בדיקות האתר.
3. פרסם דרך המסלול הבטוח:
   ```powershell
   .\scripts\workstations\publish-work.ps1 `
     -CommitMessage "SEO: <תיאור קצר>" `
     -PrTitle "SEO: <תיאור קצר>"
   ```
4. עצור ב־Draft PR ודווח את הקישור, הראיות והבדיקות. אל תפעיל auto-merge ואל תטפל ב־GitHub Token ידני.
5. רק לאחר אישור merge מפורש, מסלול `deploy-ifeel` רשאי להמשיך דרך GitHub Actions וה־runner המשרדי. אחרי פריסה מאושרת הרץ `verify-live`.

`scripts/deploy/seo-autopublish.mjs` נשמר כשם תאימות ישן, אך התנהגותו מוגבלת מעתה להאצלת העבודה ל־`publish-work.ps1` ולפתיחת Draft PR בלבד.

**נפילה בטוחה**: אם build, rebase, push או יצירת Draft PR נכשלים, אין לבצע force push, merge ידני, FTP או עקיפת runner. השאר את העבודה בענף ודווח את הסיבה.

## טריגרים ושיגור

**מתוזמן, רק כאשר קיים Scheduler מאומת במערכת הניהול**:
- יום חול → `mode: daily`
- יום ראשון → `mode: deep`
- אחרי פרסום מאמר מאושר → `mode: verify` על ה-URL החדש

תיעוד לוח זמנים אינו הוכחה שה־Scheduler פעיל. יש להציג רק תצפית רעננה ממערכת התזמון.

**ידני (אורן כותב בצ'אט)**:
- "סריקת SEO" / "תבדוק את האתר" / "מה המצב עם ה-SEO" → `mode: daily`
- "סריקה מלאה" / "deep scan" → `mode: deep`
- "תבדוק שהתיקון עבד ב-{URL}" → `mode: verify`

**פלט**:

## מלכודות ידועות — לקרוא לפני שמכריזים על "חסם טכני"

**כלל הזהב: אל תכריז על חסם טכני בלי לבדוק קוד סטטוס HTTP בפועל.**
מה שגוגל מציג ב-SERP הוא *תמונת עבר*, לא מצב השרת. דוח שמסיק "יש בעיית 301" מתוך תוצאות חיפוש — טועה.
לפני כל טענה על הפניות/סטטוס, לבצע בקשה אמיתית ולקרוא את הקוד. אם אין כלי HTTP זמין — לכתוב בדוח "לא אומת", לא להכריז.

**1. הגירת www הושלמה (21/07/2026) — לא לדווח עליה יותר.**
`www.i-feel.co.il/*` מחזיר 301 ל-`i-feel.co.il/*` (LiteSpeed, לא Netlify). אומת על כל הדפים.
העובדה שגוגל עדיין מציג כתובות `www` בתוצאות היא **פיגור עיבוד רגיל** שמתנקז מעצמו תוך שבועות — **זה לא חסם ולא דורש פעולה.**
דוח של 20/07 הכריז על זה כחסם ראשי במשך 6 ימים והפנה את כל המהלך ההתקפי לכיוון שגוי. לא לחזור על זה.

**2. עברית ב-`Location` — מקור לתוצאות 404 מזויפות.**
השרת מחזיר כותרת `Location` עם עברית ב-UTF-8 גולמי. כלים רבים (.NET/PowerShell) מפענחים כותרות כ-Latin-1 → הכתובת נהרסת → מעקב אחריה מחזיר 404 שגוי.
באודיט של 21/07 זה ייצר **54 ממצאי 404 מזויפים**. הפתרון: להמיר את המחרוזת בחזרה לבייטים ולפענח כ-UTF-8 לפני שעוקבים.
קידוד אחוזים (`%d7` מול `%D7`) **אינו** רגיש לאותיות — זו לא הבעיה.

**3. תקלות הגירה פתוחות** — הרשימה המלאה עם מיפוי 301 מוכן:
`ifeel-BMS projects/migration-audit-301-fixes-2026-07-21.md` (22 הפניות לתיקון; מתוכן 🔴 `/בית-חכם/` מחזיר 404 והוא מאונדקס בגוגל).
לפני שמדווחים על דף שבור — לבדוק אם הוא כבר ברשימה שם.

## מחזור ביצוע, ביקורת עצמאית ותיקון חוזר (חובה בכל הרצה)

**מטרה:** כל ריצת `daily`, `deep` או `verify` תפיק תוצאה מבוססת ראיות ותעבור בדיקת איכות נפרדת לפני הכרזת PASS. ביקורת אינה אישור פריסה.

### שער A: ביצוע ואיסוף ראיות
1. קרא את הדרישות הנוכחיות, בסיס ההשוואה, תאריך המדידה ומקורות הנתונים. אל תציג מיקום SERP ידני כאילו הוא ממוצע GSC ואל תסיק אינדוקס מאירוע sitemap בלבד.
2. בצע את הסריקות לפי מצב הריצה, תעד URL, תאריך, קוד HTTP, ממצאי GSC/GA4 והערכה עסקית. דרג תיקונים לפי השפעה על `בית חכם`, `בקרת מבנה`, ולאחריהם `דירה חכמה`.
3. אם אין שינוי מבוסס ראיות: רשום `NO_CHANGE`, נימוק ומדד להמשך, ולא שינוי מלאכותי כדי להראות פעילות.
4. שינוי קוד/תוכן מותר רק לפי **תיקונים אוטומטיים**, **הכנת Draft PR** ו**חוזה חיבור ל-AI Sales Manager** שבסקיל הזה. בהרצה מתוזמרת דרך Sales maturity 0 אין כתיבה כלל. אל תערוך `main`, אל תמזג ואל תפרוס בלי אישור מפורש.
5. לפני ביקורת נפרדת, הפק `execution_record`: דרישות ותנאי קבלה; מזהה ענף/commit/PR אם יש; קבצים ששונו; diff; פקודות בדיקה ותוצאות; קישורים ומדדים; חוסרים שלא אומתו.

### פקודת ההפעלה המחייבת

> **״בצע את המשימה, אחר כך הפעל סוכן משנה לביקורת עצמאית מול הדרישות, ותקן את מה שהוא מוצא.״**

הוראה זו היא **חוזה ביצוע**, לא רק ניסוח בדוח. כל orchestrator שמריץ את הסקיל חייב:
1. להשלים את שלב הביצוע ולשמור `execution_record` עם הדרישות המקוריות, הראיות וה-diff.
2. להפעיל **סוכן משנה אמיתי עם הקשר עצמאי** לפי `independent-reviewer.md`. אין להעביר לו את מסקנת המבצע או לסמן PASS מראש.
3. לקבל חזרה `review_record` עם עמידה בכל דרישה וממצאי חומרה. אם יש BLOCKER/MAJOR שניתנים לתיקון, לתקן ולהחזיר לביקורת עצמאית ולבדיקות; לכל היותר שני סבבי תיקון.
4. לבצע בדיקה סופית שהשינוי האחרון עצמו נבדק; אם אין אישור מבקר על ה-diff הסופי, הסיווג אינו `PASS_INDEPENDENT`.
5. אם למריץ אין כלי סוכן משנה או כלי קריאה לראיות: **לא להמציא הפעלה.** לבחור `BLOCKED_REVIEWER` או `REVIEW_NOT_INDEPENDENT`, לתעד מה לא זמין, ולהשאיר Draft PR לאישור. אל תהפוך סימון זה ל-PASS עצמאי או לפריסה.

**שער סיום:** אי אפשר להציג `PASS_INDEPENDENT` ללא `review_record` מזהה ריצה, תאריך, Reviewer נפרד, ממצאים, וחתימת בדיקת גרסת קוד/נתונים סופית. אין מסלול עוקף דרך משימת תזמון, SEO, GEO או דוח בראון. ההגנה על `main`, Soro ו-Gate הפריסה גוברת על בקשת תיקון.

### שער B: ביקורת עצמאית
1. **אם סביבת ההרצה תומכת בסוכן משנה נפרד**: הפעל סוכן Reviewer בעל הקשר נפרד; העבר לו דרישות מקוריות, `execution_record`, diff וראיות, **ללא מסקנת ה-PASS של המבצע**. תפקידו למצוא כשלים, לא לאשר אוטומטית.
2. **אם אין אפשרות אמיתית לסוכן נפרד**: בצע ביקורת שנייה מובנית אך סמן `REVIEW_NOT_INDEPENDENT`. אל תטען שהופעל סוכן משנה; אל תציג `PASS_INDEPENDENT`.
3. המבקר בודק מול רשימת חובה: כל דרישה בוצעה/סומנה לא זמינה; מקור ותאריך לכל טענה; קודי HTTP, canonical, sitemap, 4xx/5xx, title/H1, schema, alt, SEO טכני; התאמה לנייד ורגישות CWV; תקינות קישורים; שימור Soro Widget, ללא RSS חדש; היעדר פגיעה ב-UTM, `generate_lead`, ניתוב פניות ו-CTA; תוכן מדויק ובלתי מטעה; בדיקות build; אבטחת secrets; ובידוד השינוי מענף `main`.
4. תעד לכל ממצא `severity` (`BLOCKER` / `MAJOR` / `MINOR`), קובץ/URL, ראיה, דרישה שנכשלה, תיקון נדרש ומי אחראי. מקור לא זמין פירושו `UNVERIFIED`, לא PASS. ביקורת PR ידנית או סקירת אותו סוכן אינה שקולה לסוכן עצמאי.

### שער C: תיקון ואימות חוזר
1. תקן רק ממצאים שניתן לתקן **במסגרת הרשאות הריצה**; שינוי רגיש או שינוי שלא אושר הופך להמלצה/משימת בדיקה בלבד. אין עקיפת הרשאות לצורך PASS.
2. הפעל מחדש את הבדיקות הרלוונטיות ואת כל בדיקות השער שהושפעו; תעד את ההבדל בין לפני/אחרי ואת תוצאת ה-build. בבדיקת שינוי קוד, בקש מאותו Reviewer נפרד לבקר מחדש את ה-diff הסופי אם הוא זמין.
3. חזור על **ביקורת → תיקון → בדיקות** עד שאין `BLOCKER` או `MAJOR` שניתן לתקן, עם **מקסימום שני סבבי תיקון** להרצה. אם יש ממצא שלא נפתר, כשל חוזר, מקור לא זמין או צורך באישור אורן: עצור, שמור את המצב ב-Draft PR/דוח, ודווח `FAIL` או `BLOCKED` עם הסיבה. אין לולאה אינסופית ואין PASS בכוח.
4. `PASS_INDEPENDENT` מותר רק כשהמבקר באמת נפרד, כל תנאי הקבלה אומתו ואין ממצא חוסם. `PASS_SELF_REVIEW` מותר רק לציון תקינות טכנית עם סימון מפורש שהביקורת אינה עצמאית. **אף PASS אינו מהווה אישור merge, פריסה או שינוי production.**
5. אימות `verify-live` ו-GSC לאחר פריסה אפשריים רק **אחרי** אישור merge ופריסה נפרדים; אל תתאר שיפור בדירוג כעובדה לפני חלון נתונים אמיתי.

### פלט חובה קצר (נוסף לדוח הקיים, בלי לשנות את סדר North Star)
```text
QA: PASS_INDEPENDENT / PASS_SELF_REVIEW / FAIL / BLOCKED / NO_CHANGE
ביצוע: [מה נבדק/שונה, קישור לענף או Draft PR אם נוצר]
ביקורת: [סוכן משנה נפרד: כן/לא; מספר BLOCKER/MAJOR/MINOR; 1-2 ממצאים מרכזיים]
תיקון ואימות: [מה תוקן, אילו בדיקות הורצו מחדש, תוצאות]
חסמים: [לא זמין/דורש אישור, אם רלוונטי]
פריסה: לא בוצעה / אושרה בנפרד (כולל אסמכתה)
```

**מגבלת תזמון:** זמני הריצה המופיעים בטבלה הם אומדנים בלבד; אין לדלג על ביקורת כדי לעמוד בהם. מתוזמן אינו מצדיק כתיבה או פריסה שלא אושרו. רשום בבירור כשסביבת ההרצה אינה מאפשרת סוכן משנה או build.


## GEO: נוכחות מותג בתשובות AI לצד דירוגי SEO

**מתכונת מאושרת למדידה:** 10 שאלות עבריות קבועות × 4 מנועים = **40 תשובות צפויות**. השאלות ומזהי השאלות בקובץ `ai-visibility-prompts.md` בגרסת `ifeel-geo-10-v1`: 5 וילות ובתים פרטיים, 3 בקרת מבנה/Desigo/DDC/DALI, 2 יזמים וקבלנים. אין לגוון ניסוח או להוסיף תשובות מלאכותיות.

### שורת GEO קבועה בדוח הבוקר (מיד מתחת ל-North Star)
```text
GEO | I Feel הוזכרה: {M}/{N} תשובות שנבדקו (כיסוי {N}/40) | קישור לאתר: {C}/{N} | המתחרה המוביל: {שם + מספר אזכורים או לא זמין} | Google AI: {מספר חשיפות + חלון זמן + מקור או לא זמין} | עדכון המדגם: {תאריך}
```
- שורת GEO מופיעה **בכל בוקר**, אך תוצאות ארבעת המנועים מבוססות על **הרצת יום ראשון האחרונה שנשמרה עם ראיות**. הצג תאריך מדגם וגילו; אל תכתוב כאילו נערכה בדיקה של ארבעת המנועים היום אם זה לא קרה. אם אין מדגם מאומת, השתמש `לא זמין (0/40 נבדקו)`, **לא** `0/40 הוזכרה`.
- `M` הוא מספר **תשובות** שבהן I Feel הוזכרה במפורש; `C` מספר תשובות המכילות קישור ממשי לדומיין. `N` תשובות שהתקבלו ונבדקו מתוך 40; דיווח `M/40` או `C/40` מותר רק אם N=40. המתחרה המוביל הוא המתחרה עם הכי הרבה תשובות שבהן הוזכר, וציין תיקו אם קיים.
- מדד ה-Google AI impressions הוא **נפרד** מה-40: דוח `Search Console → Performance → Generative AI (Search)` מציג חשיפות AI Overviews ו-AI Mode, לא תשובות 10 השאלות ולא ציטוטים מסוימים. לפי תיעוד גוגל הדוח זמין מאז יוני 2026 והפריסה העולמית הסתיימה באוגוסט; ייתכן שלא יוצג בנכס עם מעט חשיפות. <https://developers.google.com/search/blog/2026/06/gen-ai-performance-reports> ו-<https://support.google.com/webmasters/answer/16984139>. לעולם אל תוסיף את החשיפות האלה לחשיפות החיפוש הרגילות, כי הן כבר כלולות בהן.
- אם אין גישה ישירה לדוח הייעודי דרך כלי מורשה, הצג `Google AI: לא זמין (אין גישה לדוח הייעודי)` ולא אפס. **אסור** להחליף אותו ב-impressions כלליים מ-Search Analytics של Windsor.

## Mandatory sitemap and 4xx gate

Before every production publish or SEO-driven page change, run a full live sitemap integrity check. Every URL listed in `public/sitemap.xml` must resolve on production to HTTP 200 after deploy. Any 4xx or 5xx response is a release-blocking SEO defect until investigated and corrected.

Rules:
- Never publish a new sitemap URL without verifying the exact live URL returns 200.
- Treat Unicode/Hebrew slugs as high-risk: verify UTF-8 encoding, canonical URL, internal links, generated route, and live server response. Prefer stable ASCII slugs when a Unicode slug causes encoding ambiguity or server inconsistency.
- Detect duplicate sitemap URLs and remove duplicates before release.
- If Google Search Console reports `Blocked due to other 4xx`, immediately identify the exact affected URLs, reproduce the live HTTP status, fix the route/link/sitemap source, redeploy, and re-check.
- After deployment, re-fetch the live sitemap and test every listed URL. Do not report the issue as fixed until the production crawl has zero unexpected 4xx/5xx results.
- Add this check to the daily SEO health review and to every `verify-live`/deployment verification flow.
- Record the root cause and prevention rule when a new class of indexing error is discovered, so the same failure is not repeated.
